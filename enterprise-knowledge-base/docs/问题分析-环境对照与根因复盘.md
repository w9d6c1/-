# 问题分析：环境对照与根因复盘

> 本文档基于 2026-08-10 会话期间的实测证据编写，仅做分析记录，不包含修复实施。
> 核心结论：当前本地与 Docker **均为 Vite 开发服务器模式**，用户此前汇总中的"脏包 / pdf.js CSP / 两套机制"等论断与实际情况不符；已确认的真实故障为"宿主机失效代理残留"与"CSP 缺失 blob:"，两者均已修复。

---

## 一、当前运行环境的事实基线（最关键）

### 1.1 启动方式
- `start.ps1` 调用 `docker compose --project-directory $composeDir up -d`，未指定 `-f`，因此实际加载的是 **`docker-compose.yml`（开发配置）**，而非 `docker-compose.prod.yml`。

### 1.2 前端容器运行的是 Vite 开发服务器（不是 Nginx 静态服务）

实测证据（`docker inspect` + 容器内 `ps`）：

| 项目 | 实测值 |
|------|--------|
| `kb-app` 启动命令 | `npm run dev -- --host 0.0.0.0` |
| `kb-frontend` 启动命令 | `npm run dev -- --host 0.0.0.0` |
| `kb-app` 运行进程 | `node .../vite/bin/vite.js --host 0.0.0.0` |
| `kb-app` 容器入口 | `docker-entrypoint.sh`（Node 镜像，非 nginx） |
| nginx `upstream frontend` | `server frontend:5173;`（Vite 端口） |
| nginx `upstream react_app` | `server app:5175;`（Vite 端口） |

### 1.3 对外页面由 Vite 实时编译提供

`https://localhost/app/` 返回的 HTML 包含：

```html
<script type="module">import { injectIntoGlobalHook } from "/app/@react-refresh"; ...</script>
<script type="module" src="/app/@vite/client"></script>
<script type="module" src="/app/index.html?html-proxy&index=0.js"></script>
<script type="module" src="/app/src/main.tsx"></script>
```

这些是 **Vite DevServer 的 HMR/模块代理能力**，只在开发服务器模式下出现。

### 1.4 核心结论

> **当前本地与 Docker 运行机制几乎相同**：都是 Vite DevServer（内存编译 + 模块代理 + HMR）。
> 两者唯一的差异是：Docker 链路在 Vite 外层多了 **nginx 反代 + WAF + CSP/TLS 响应头** 三层。
> 因此"本地是开发模式、Docker 是生产 dist 静态服务"的对比框架**不成立**。

## 二、用户汇总逐条判定

| # | 用户论断 | 判定 | 证据 |
|---|---------|------|------|
| 1.1 | dist 存在脏包，生产 Docker 混入 Vite HMR 代码 | ❌ 不成立 | 当前 Docker 容器跑 `npm run dev`，**从未读取 dist**（nginx upstream 指向 5173/5175）。`app/dist/index.html` 引用的是干净生产产物：`<script type="module" crossorigin src="/app/assets/index-Cv49DVJH.js">`，无任何 HMR 代码 |
| 1.2 | 构建未锁 NODE_ENV=production | ⚠️ 部分成立（仅影响未来 prod 部署） | `docker-compose.prod.yml` 才使用 `target: production`（Nginx serve dist）。`npm run build` = `tsc -b && vite build`，Vite 默认 build 即 production，但未显式 `--mode production`；根 `.env` 存在 `VITE_API_BASE_URL=http://localhost:8000`，有被打进产物的风险。**当前 dev 模式不受影响** |
| 1.3 | `app/?token` websocket 是脏包导致的挂起请求 | ❌ 不成立 | Vite 官方客户端源码 `node_modules/vite/dist/client/client.mjs:245` 定义 `token=${wsToken}`——这是 **Vite HMR WebSocket 的正常鉴权参数**。当前 Docker 跑 dev server，出现该请求属正常现象 |
| 2.1 | CSP 拦截 `pdf.min.mjs`（blocked:csp） | ❌ 不成立 | `pdf.min.mjs` 仅存在于 `node_modules/.pdfjs-dist-3NWdfSEA/`（npm 重装残留的隐藏缓存目录）。**无任何 package.json 依赖它，前端源码无任何导入**。Vite 不会打包，浏览器不会请求它，不存在 blocked:csp |
| 2.2 | nginx `proxy_pass` 与 Vite `server.proxy` 未对齐 | ⚠️ 有合理性（架构事实，非故障根因） | nginx 将 `/api` → `waf:8080`（再转 `backend:8000`）；Vite dev proxy 将 `/api` → `backend:8000`。路径一致，转发链路不同（nginx 多经 WAF 层）。属于架构设计差异 |
| 2.3 | CSP 未加 `always` 不生效 | ⚠️ 部分正确（潜在缺陷，非已发生故障） | `docker/nginx/conf.d/default.conf:47` 的 CSP `add_header` 无 `always`。`add_header` 只在特定响应状态码生效，404/502 等错误响应不会带 CSP 头。属配置缺陷 |
| 2.4 | `/app/` 子路由 base 需与 vite.config 匹配 | ✅ 正确（当前已匹配） | `app/vite.config.ts` 设置 `base: '/app/'`；nginx `location /app/` → `react_app`。二者一致，无路径不匹配问题 |
| 3 | 本地 Vite dev 与 Docker 生产 Nginx 是两套机制，本地正常不代表 Docker 正常 | ❌ 核心前提错误 | 见第一部分：**当前 Docker 也是 Vite dev server**。真正的 Docker 独有差异是 nginx 层的 CSP / 代理 / WAF / TLS，而非"dist vs 内存编译" |
| 4 | 浏览器缓存干扰排错 | ✅ 普遍成立 | 通用 Web 项目干扰项，无法从代码证实，但排错时需硬刷新/无痕窗口排除 |
| 5.1 | Docker 下 `pdf.min.mjs blocked:csp`，PDF 预览异常 | ❌ 不成立 | 见 2.1，前端无 pdfjs 依赖与导入，无此资源请求 |
| 5.2 | Network 面板出现 pending 状态 Vite HMR websocket | ✅ 现象真实但归因错误 | 见 1.3，这是 **dev server 的正常 HMR websocket**（`app?token=...`），不是故障 |
| 5.3 | 接口 200 但前端业务表现异常 | ⚠️ 有真实案例但根因不同 | 已确认的真实案例是照片显示异常（根因见第三部分 CSP 缺 `blob:`），非"脏包+代理未对齐" |
| 5.4 | 本地一切正常，一上 Docker 就出问题 | ⚠️ 现象部分属实，根因被误判 | 真实差异仅在 nginx 层策略（CSP）与宿主机代理残留，与构建产物无关 |

## 三、已确认的真实故障与修复记录

### 3.1 故障一：容器外网请求全部失败

- **现象**：AI 文章生成器大量功能不可用；容器内 `api.deepseek.com`、`www.baidu.com` 全部 `ConnectError`；WSL2 内 TLS 握手被重置。
- **根因**：宿主机残留系统代理配置 `ProxyEnable=1, ProxyServer=127.0.0.1:7897`，但 7897 端口无任何进程监听（代理软件已停止）。Docker Desktop 内置代理 `http.docker.internal:3128` 跟随系统代理，将容器 HTTPS 出站转发到失效的 `127.0.0.1:7897` → 连接被拒。
- **实测错误**：`connecting to 127.0.0.1:7897: dial tcp ... actively refused`
- **影响**：LLM 调用（DeepSeek）、四平台热榜抓取、视觉模型等所有依赖外网的 AI 功能。
- **修复**：清除系统代理残留（`ProxyEnable=0`，清空 `ProxyServer`），重启 Docker Desktop。
- **验证**：容器 HTTPS 外网 200；LLM 调用返回 "OK"；微博/知乎/头条/百度热榜各返回 30 条。

### 3.2 故障二：照片库照片无法显示

- **现象**：照片库、文章配图、AI 写作照片匹配中的图片全部无法显示。
- **根因**：前端通过 `fetch(blob)` → `URL.createObjectURL(blob)` 生成 `blob:` 临时 URL 显示图片（`app/src/api/photos.ts:111`、`PhotoMatcher.tsx:40`、`ArticleDetail.tsx:94`、`PublishManager.tsx:179`）。但外层 nginx CSP 头（`docker/nginx/conf.d/default.conf:47`）为 `img-src 'self' data: https:`，**缺少 `blob:`**，浏览器按 CSP 规则阻止所有 `blob:` 图片。
- **实测**：后端照片接口 200、`image/jpeg`、内容完整（MinIO 154 张照片均在）；问题完全出在浏览器 CSP 拦截层。
- **修复**：CSP `img-src` 增加 `blob:` → `img-src 'self' data: blob: https:`，`nginx -s reload`。
- **验证**：CSP 响应头已含 `blob:`；照片经 nginx 返回 200。

### 3.3 网络连通性核验（排除 WAF/网络因素）

- 17 个 kb-* 容器全部在同一网络 `enterprise-knowledge-base_kb-network`（172.19.0.0/16）。
- 链路 `nginx → waf:8080`、`nginx → backend:8000`、`waf → backend:8000`、`app → backend:8000`、`backend → waf` 全部 200。
- 基础设施端口（mysql/redis/es/milvus/minio/etcd/publisher）TCP 全部 OPEN。
- WAF 日志无任何 403/拦截/CRS 告警；nginx 日志中照片请求（含中文文件名）全部 200。

## 四、prod 构建链路审查（问题清单，暂不修复）

以下基于 `docker-compose.prod.yml` + Dockerfile prod stage + 内部 nginx 配置的静态审查，供未来生产部署参考：

| # | 问题 | 位置 | 风险等级 |
|---|------|------|---------|
| 1 | `npm run build` 未显式 `--mode production` | `app/package.json:8`、`frontend/package.json` | ⚠️ 中 — Vite 默认 build 即 production，但根 `.env` 的 `VITE_API_BASE_URL=http://localhost:8000` 可能被打入产物，生产环境将请求错误地址 |
| 2 | prod 内部 nginx（app/frontend）无 CSP 头 | `app/docker/nginx-app.conf`、`frontend/docker/nginx-frontend.conf` | ⚠️ 中 — 仅 nosniff/X-Frame/Referrer 三头；若生产走外层 nginx 则外层已有 CSP，需确认职责边界 |
| 3 | 外层 nginx CSP 无 `always` | `docker/nginx/conf.d/default.conf:47` | ⚠️ 低 — 错误响应不携带 CSP |
| 4 | prod 环境未关闭 `DEBUG=true` / `LOG_LEVEL=DEBUG` | 根 `.env` | ⚠️ 低 — 生产建议关闭调试输出 |
| 5 | prod frontend 健康检查用 `curl`，但 `nginx:1.27-alpine` 镜像无 curl | `docker-compose.prod.yml:136` | ⚠️ 中 — 健康检查可能始终失败，建议改用 `wget` |
| 6 | `dist` 构建时间早于最新源码（app dist 为 2026-08-07） | `app/dist`、`frontend/dist` | ⚠️ 低 — 生产部署前需重建 |

## 五、一句话结论

> 用户汇总将故障归因于"脏构建产物 + pdf.js CSP + 本地/生产两套机制"，但实测证明当前 Docker 与本地同为 **Vite 开发服务器模式**，不存在该机制差异；真实故障只有两个——**宿主机失效代理残留（127.0.0.1:7897）** 与 **CSP 缺失 `blob:` 导致照片无法显示**，二者均已修复。prod 构建链路存在若干待办项（NODE_ENV 锁定、健康检查、调试开关），需在真正启用生产部署时处理。
