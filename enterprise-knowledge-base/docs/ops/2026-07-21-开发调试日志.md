## 三、Milvus coll_internal 加载超时修复（B13）

### 3.1 诊断

| 维度 | 发现 |
|------|------|
| coll_internal | 386 实体 × 1024 维 + `VARCHAR(65535)` content 字段 |
| 索引 | IVF_FLAT, nlist=128 |
| 内存 | 260MB / 7.3GB（仅 3.5%）— 非资源不足 |
| 根因 1 | `load(timeout=10)` 对 386 实体不够 |
| 根因 2 | 无 `utility.load_state()` 检查，每次调用都重新 load |
| 根因 3 | `preload_collections` 未在 startup 调用 |

### 3.2 修复

**文件：** `retrieval/milvus_client.py` + `main.py`

| 改动 | 内容 |
|------|------|
| 超时 | `load(timeout=10)` → `_LOAD_TIMEOUT = 30` |
| load_state 检查 | 新增 `utility.load_state()` 检测，已 `Loaded`/`Loading` 则跳过 |
| 空 collection 跳过 | `num_entities == 0` 直接缓存，不触发 load |
| 启动预热 | `main.py` lifespan 中 `create_task(preload_collections())` |
| 连接去重 | 新增 `_ensure_connected()` 避免重复 `connections.connect` |

**验证：**

```
修复前: coll_internal load → 10s 超时 ❌
修复后: coll_internal load → 0.0s ✅（启动预热 + load_state 跳过）
```

## 十六、敏感词删除后仍拦截排查

### 16.1 问题描述

用户反馈「前端删除敏感词，但智能问答还是禁用我」。

### 16.2 排查过程

追踪了完整链路：
1. 前端 `DELETE /api/admin/sensitive-words/{id}` / `bulk-delete` → 到达后端 ✓
2. 后端 `db.delete(sw)` + `db.commit()` → 数据库删除成功 ✓
3. `_reload_word_caches(db)` → `load_words_from_db(db)` → 更新全部三个内存缓存 ✓

日志确认：`07:57:48` 用户批量删除 IDs 101-105，删除后立即 `SELECT * FROM sensitive_word` 重载缓存，流程完整无误。

### 16.3 根因

系统中存在**两类不同作用的词**：

| 类别 | `word_type` | API 路径 | 效果 |
|------|-----------|----------|------|
| **敏感词** | `sensitive` | `/api/admin/sensitive-words` | 输出中替换为 `***` |
| **禁答词** | `forbid` | `/api/admin/forbid-words` | **直接拦截整个请求** |

用户在前端「敏感词」标签页删除的是 `sensitive` 类型词，但实际拦截查询的是「禁答词」标签页中的 `forbid` 类型词（如"对比""竞品""排名""内部""成本"等 28 个）。

### 16.4 结论

后端代码逻辑正确，删除 → 提交 → 缓存重载全链路完整。问题为用户混淆了两个标签页。被拦截的查询可通过 API 返回的 `block_reason` 字段定位具体违禁词。
